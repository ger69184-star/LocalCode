# Лицензирование и защита от копирования

Документ для владельца продукта. Пользователю достаточно раздела «Лицензия» в
настройках и файла `LICENSE`.

## Как это работает

- Проверка **полностью офлайн**: ключ — это строка `LC1.<данные>.<подпись>`
  с подписью Ed25519. Приложение проверяет её открытым ключом из
  `license-pub.pem`. Интернет и сервер лицензий не нужны.
- **Закрытый ключ** (`license-keys/private.pem`) хранится только у вас и в git не
  попадает (`.gitignore`). Он нужен для выпуска ключей и подписи целостности.
  Если он потерян — придётся выпустить новую пару, и все старые ключи станут
  недействительными.
- **Привязка к компьютеру** (`--mid`): в ключ попадает ID машины
  (sha256 от системного идентификатора + случайного `machine-id` установки).
  Ключ без `mid` работает на любом компьютере — это удобно для «семейных» и
  корпоративных планов, но хуже защищает от копирования.
- **Пробный период** отсчитывается от первого запуска
  (`~/.localcode/license-first-run`) и задаётся в `license-policy.json`.
- **Целостность**: `integrity.json` — подписанный манифест sha256 для основных
  файлов (`server.js`, `license.js`, `hw.js`, `public/*.js`, `public/index.html`).
  Стили `public/style.css` намеренно **не** входят: их разрешено менять.
  Политика `integrity: "warn"` только пишет предупреждение, `"block"` переводит
  приложение в состояние `tampered` и отключает ИИ-функции.

## Что закрывается лицензией

| Состояние | Что работает |
|---|---|
| `trial` | всё, включая ИИ, до конца пробного периода |
| `licensed` | всё, пока действует ключ |
| `expired` / `invalid` | редактор, дерево файлов, чтение/запись/удаление файлов, git, терминал, чат-история — **без** ИИ |
| `tampered` (при `block`) | как `expired`, плюс сообщение о подмене файлов |
| `disabled` (нет `license-pub.pem`) | всё: режим разработки, защиты нет |

Блокируются только «дорогие» и ИИ-зависимые маршруты:
`/api/chat`, `/api/complete`, `/api/tool`, `/api/models`, `/api/keys/*`,
`/api/pull`, `/api/catalog`, `/api/installed`, `/api/stt*`, `/api/term/run`.
Проверка выполняется на сервере, поэтому обойти её правкой страницы в браузере
нельзя: без ключа сервер просто не выполнит запрос.

## Выпуск ключей

```bash
# 1. Один раз: пара ключей. Открытый устанавливается в приложение.
node tools/license-cli.js keygen --out ./license-keys --install

# 2. Ключ покупателю (бессрочный, привязанный к его ID компьютера)
node tools/license-cli.js issue --key ./license-keys/private.pem \
    --plan pro --perpetual --mid <ID из настроек> --email user@example.com

# 3. Ключ с ограничением по времени
node tools/license-cli.js issue --key ./license-keys/private.pem --plan trial-ext --days 30

# 4. Проверка и статус
node tools/license-cli.js verify --token 'LC1....'
node tools/license-cli.js status

# 5. После любых изменений в коде — заново подписать целостность
node tools/license-cli.js sign --key ./license-keys/private.pem
```

**Закрытый ключ нельзя коммитить, публиковать, передавать покупателям или
хранить в облаке вместе с исходниками.** Резервная копия — на съёмном носителе
или в менеджере секретов.

## Настройка политики

`license-policy.json` в папке приложения:

```json
{ "mode": "trial", "trialDays": 14, "bindMachine": true, "integrity": "warn" }
```

- `mode`: `off` — лицензирование выключено; `trial` — пробный период, затем
  ключ; `enforce` — ключ нужен с первого запуска (`trialDays: 0`).
- `bindMachine`: проверять привязку ключа к компьютеру.
- `integrity`: `off` | `warn` | `block`.

Если файл политики удалён, действуют значения по умолчанию (пробный период
14 дней, `warn`). Если удалён `license-pub.pem`, лицензирование выключается —
это удобно для разработки, но в поставке открытый ключ должен быть на месте.

## Честно о границах защиты

Код приложения написан на JavaScript и выполняется на компьютере пользователя.
Любой, у кого есть права администратора на своей машине, теоретически может
изменить код и снять проверку. Задача этой защиты — не «абсолютная
невзламываемость», а экономическая невыгодность пиратства:

1. ключи подписаны, подделать их без закрытого ключа нельзя;
2. проверка идёт на сервере, а не в браузере;
3. манифест целостности подписан, поэтому «тихая» правка файлов обнаруживается;
4. один ключ = один компьютер (при `bindMachine`), передача ключа другу
   бесполезна;
5. все проверки офлайн — их нельзя «отключить» блокировкой сервера лицензий.

Для более строгой защиты в будущем: серверная выдача ключей с лимитом активаций,
обфускация/упаковка в исполняемый файл, периодическая онлайн-проверка (сейчас
намеренно не используется, чтобы приложение оставалось локальным).

## Что ещё усилено в этом раунде

- лимит частоты запросов к API (всплеск 60, восстановление 8/с);
- ограничение глубины обхода каталогов (24 уровня) и запрет обхода симлинков в
  списке файлов;
- лимит вывода терминала (20 МБ на процесс, 12 процессов, 400 тыс. символов в
  интерфейсе) и обратное давление при медленном клиенте;
- ограничение длины команды терминала.

Сообщения об уязвимостях — по правилам из `SECURITY.md`.
